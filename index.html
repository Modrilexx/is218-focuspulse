1. Research Question, Audience & Epistemic Boundaries

Research Question: How can a solo student build a secure, testable, bounded full-stack web application (account access → useful interaction → saved record → private dashboard → account maintenance) using Python, Flask, and SQLite while testing whether the Strategy design pattern improves maintainability over a simpler procedural function?

Target Audience: College students and junior analysts who want a lightweight, private way to log focused study/work sprints (duration, course/project tag, focus rating) and review personal productivity trends without bloated subscription apps.

Verified Facts

  • Flask supports modular request-scoped relational database connections and server-side session workflows (Flask Docs).
  • SQLite stores an entire relational database in a single file and is officially suited for low-to-medium traffic apps and Python data analysis (SQLite.org).
  • OWASP recommends strong password hashing, generic login error messages, and secure session handling (OWASP Auth).

Interpretations

  • A bounded study/sprint logger fits a Business & Information Systems + Data Analytics focus better than a browser game because saved records naturally feed summary analytics.
  • Using SQLite removes external database hosting complexity during early slices while keeping real SQL queries and schema constraints.

Assumptions (To Test Later)

  • Students will log sprints in under 20 seconds if the form only asks for title, duration, tag, and 1–5 focus rating.
  • Multiple scoring formulas (simple streak vs. weighted focus score) will justify testing a Strategy pattern; if not, a plain function will win.

2. Comparing Two Bounded Creative Concepts

Chosen Concept

Option A: FocusPulse (Bounded Non-Game App)

A private study and project sprint logger where authenticated users record bounded work sessions (15–180 minutes), categorize them by course/topic, and view weekly totals and focus scores on a private analytics dashboard.

  • Workflow Promise: Sign up / sign in → Log a focus sprint → Persist validated sprint record in SQLite → Inspect private history & summary metrics → Update display name / password or delete account.
  • Why Chosen: Directly showcases SQL aggregation, server-side validation, and analytics thinking relevant to Data Analytics with Applied AI roles.
Alternative Considered

Option B: DeckDuel (Bounded Trivia Game)

A timed 5-question browser quiz game where users log in, play a short round, save high scores, and view their personal score history.

  • Tradeoff: Fun interaction, but requires authoring/curating a question bank and focuses more on game-state UI than on structured data-record analytics.
  • Decision: Declined in favor of FocusPulse to keep scope tightly aligned with data analytics and clean server-side CRUD + aggregation.

3. Review 2 SPEC — What I Chose to Build & Planned Checks

Chosen Build Scope (Review 2 SPEC): Build FocusPulse with Python 3.12 + Flask + SQLite + Jinja2 + pytest + Ruff. The first working slice implements server-side registration/login, logging a single validated sprint record, rendering the user's private sprint history + summary metrics, and signing out.

Five Prioritized User Stories & Acceptance Criteria

ID User Story Acceptance Criteria Priority
US-1 As a student, I can register and sign in with a unique email and password so my study logs stay private. Passwords hashed with Werkzeug/scrypt; duplicate emails rejected; session cookie set with HttpOnly and SameSite=Lax; sign-out clears session. P1 (Slice 1)
US-2 As a signed-in user, I can log a bounded focus sprint (topic, duration 5–240 min, focus score 1–5) so I can track my work. Server validates all bounds (rejects 0, negative, or >240 min); valid submission inserts one row tied to session["user_id"] and redirects to dashboard. P1 (Slice 1)
US-3 As a signed-in user, I can view my private sprint history and summary dashboard (total minutes, average focus, productivity score). Queries filter strictly by user_id; unauthenticated requests redirect to login; another user's records are never visible. P1 (Slice 1)
US-4 As a signed-in user, I can switch between two productivity scoring views (Simple Total vs. Focus-Weighted Score) to compare my habits. Uses interchangeable scoring strategies (pattern experiment) and recalculates dashboard metric deterministically from saved SQLite rows. P2 (Slice 2)
US-5 As a signed-in user, I can update my display name or password and delete a mistaken sprint entry. Password update verifies current password first; delete checks record ownership (user_id match) before deleting. P2 (Slice 2)

Uncertain Creative Experiment: Strategy Pattern vs. Simple Function

Hypothesis: Encapsulating sprint scoring logic behind a Strategy pattern (ScoringStrategy protocol with SimpleMinutesStrategy and WeightedFocusStrategy) will make adding new analytics formulas cleaner and easier to unit-test than a single conditional if/elif function.

Uncertainty & Honest Exit Criteria: With only 2 scoring modes, a class hierarchy might add boilerplate without real payoff. During Slice 2, I will implement both side-by-side in a branch, compare line count, readability, and test clarity, and keep the simpler approach if the pattern feels forced. Status: Planned.

4. Technical Architecture Sketch & Data Model

5. Six-Point Planning Checklist (Document Before You Build)

1. Agile Work Plan

In Scope: Email/password auth, bounded sprint logger, private history & KPI dashboard, scoring strategy toggle, profile/password update.

Out of Scope: Social leaderboards, OAuth third-party login, real-time Pomodoro WebSockets, mobile native app.

Milestones: M1 Plan/SPEC (Nov 19) → M2 Slice 1 Auth + Log + Dashboard → M3 Slice 2 Strategy Experiment + Account Maintenance + Peer Retry.

2. Technical Architecture & Tradeoffs

Chosen Stack: Python + Flask + SQLite + Jinja2 (free local dev, zero DB server setup, strong Python analytics alignment).

Alternative Compared: Node.js/Express + PostgreSQL. Rejected for this bounded solo project because Postgres provisioning adds deployment overhead not needed for low-concurrency course workloads (SQLite.org).

Security: Parameterized SQL queries, salted password hashes, CSRF tokens on POST forms, HttpOnly cookies.

3. Code Architecture & SOLID

  • Single Responsibility: Route handlers only parse HTTP/render templates; services/ owns business rules; repositories/ owns SQL.
  • Open/Closed & Dependency Inversion: Dashboard service depends on a ScoringStrategy interface rather than concrete scoring classes.
  • Simplicity Guardrail: No Factory/Observer/Singleton patterns—only one targeted Strategy experiment.

4. Efficient Testing Strategy

  • Unit tests (fast, local + CI): Validation bounds (0, 5, 240, 241 min) and scoring formulas via pytest.
  • Integration tests (Flask test client + temp SQLite): Auth flow, session cookies, and cross-user isolation.
  • End-to-End (1–2 smoke paths): Sign up → log sprint → verify dashboard total → sign out.

5. Code-Quality Checks

Use Ruff for fast linting and formatting (ruff check . and ruff format --check .) on every commit locally and in GitHub Actions CI. Pull requests will not merge until lint and pytest pass.

6. Build & Review Sequence

  1. Initialize Flask app factory + SQLite schema + pytest fixture.
  2. Implement US-1 (auth) + US-2 (sprint log) + US-3 (dashboard) as Slice 1.
  3. Run peer review on Slice 1, log GitHub Issues, implement Slice 2 (US-4 Strategy experiment + US-5 account maintenance).
